# 工程判断：让方案随约束变化

用于技术选型、缺陷诊断、实现偏离或高成本决策；不要求小改动另写一份架构报告。已有设计和风险规则仍然有效，本参考不授予生产操作、扩大范围或自行通过评审的权限。

## 从故障机制选方案，而不是从技术名称选方案

在现有技术方案或交接中保留能改变决定的内容：已观察的事实、尚未证实的假设、必须守住的不变量、最有竞争力的替代方案，以及什么新证据会让当前选择失效。证据不足时，先做最小可区分实验，不把猜测写成根因。

| 场景和决定因素 | 优先考虑的处理 | 容易误用的做法 | 改变选择所需的证据 |
|---|---|---|---|
| 可复现的局部边界错误，影响集中、契约不变 | 围绕失败输入和不变量做局部修复，补回归；沿真实调用路径确认范围 | 借修 bug 重构整层；只改输出掩盖错误状态 | 多入口重复同一故障机制、边界无法容纳正确性，才提出结构调整 |
| 偶发错误，日志只显示最后一个异常 | 对齐请求、时间、版本、输入和依赖结果，提出可区分的假设并收集证据 | 把最后一条异常当根因；用重试或延长超时掩盖未知故障 | 能稳定触发或排除某个假设的实验，才足以支持修复方向 |
| 外部副作用超时，可能已成功；请求会重复 | 明确业务操作身份、持久化状态和未知结果的恢复；核查下游去重/查询能力、并发与崩溃窗口 | 把超时当失败直接重做；仅靠进程内锁；声称本地事务覆盖外部系统 | 只有确认下游幂等或可核实结果，才决定何时安全重试；无法判定则保留待核对状态 |
| 小而有界、需即时结果的操作 | 优先沿现有同步路径实现，明确超时和资源上限 | 为“可扩展”先引入队列、任务中心和分布式状态 | 代表性负载、耗时或恢复需求超出现有边界，才考虑异步 |
| 长耗时、可中断、需要恢复的批处理 | 持久任务身份、进度与结果，设计部分失败、取消、重入、背压和恢复；按现有能力选择执行机制 | 只把请求丢进后台线程；把入队成功当业务完成；假定队列天然避免重复 | 数据规模、失败恢复和交互约束决定是否需要队列，不由“批量”一词决定 |
| 多版本并存且必须保留数据的模式变更 | 先定义兼容窗口与数据不变量，再设计渐进迁移、校验和切换；破坏性步骤单独授权 | 新代码上线后立即删旧字段；把回滚应用等同于恢复数据 | 已验证旧读写方退出、数据校验通过且恢复路径可用，才考虑收缩旧结构 |
| 性能不达标，但瓶颈未测明 | 用代表性请求/数据找出主要耗时与资源消耗，再选查询、算法、缓存或架构方案 | 未测量先上缓存/拆服务；只测空数据；忽略缓存失效和新鲜度 | 测量能说明瓶颈及收益；若风险转为一致性或运维成本，重新比较方案 |

这些是条件化候选，不是固定技术配方。例如本地一次性数据转换不必套在线无停机迁移；但“可重新生成”必须有事实支持，不能自行认定用户数据可丢弃。

## 把关键决定变成可反驳的设计

- **身份与状态**：一次操作如何识别；成功、失败和未知是否分开；哪个存储或外部系统是事实来源。跨边界副作用不能仅由单进程测试证明。
- **不变量与失败窗口**：选出真正不能发生的结果，例如同一业务操作重复产生副作用、迁移后丢失记录。给测试角色可控的时间、并发、依赖故障或重启接缝，不用任意等待假装控制顺序。
- **替代与可逆性**：对昂贵决定比较一个可信替代方案，不堆选项；写明取消某个抽象能否仍完成任务。可逆必须说明逆转的是代码、流量还是数据，不能笼统写“支持回滚”。
- **真实入口**：内部 API 正确而普通用户入口仍走旧路径，不能交付。mock 可以证明调用协议和故障分支，不能证明真实依赖可用或结果语义正确。

若任务包含模型/启发式结果，将确定性的输入输出契约、权限和恢复，与依赖样本评估的语义质量分开；不要把 schema 校验或固定示例冒充智能能力。具体依赖契约需查当前实现或权威文档，不能从模式表猜测。

## 交接要让别人能挑战你的判断

把「观察 → 假设 → 选择 → 证据 → 残余风险」融入已有技术方案或实现说明，不强制新增文档。给测试角色实际运行入口、源版本、代表性失败输入、观测点及未证明的部分；告诉评审者哪条假设失效会要求重新设计。开发自测只说明开发获得了什么证据，不代替独立验证。
