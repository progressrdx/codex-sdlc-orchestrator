# 协调判断：选择最能减少不确定性的下一步

仅用于已经激活的项目，在读取真实状态后帮助路由工作。不是新角色、激活入口或状态规则；不得因此为普通问题开启团队流程。主 Skill 中的阶段、预算、角色独立性、风险升级和用户授权仍然具有约束力。

## 先识别卡住的是什么

下一步应针对一个有证据的未决问题，交给有权解决它的角色，要求能够支持下一项决定的输出。不要把每次反馈都变成全团队重做，也不要因问题短就绕过当前状态。

| 已观察情况 | 下一步及责任边界 | 不应做什么 |
|---|---|---|
| 用户目标或成功标准有歧义，会改变设计/验收 | 由产品明确关键选择；只把无法合理推断且影响结果的决定交给用户 | 让开发猜业务政策；靠实现原型悄悄锁定未确认需求 |
| 已确认目标不变，实际行为违约 | 根据受影响阶段和当前证据安排工程诊断/修复、测试独立复验；按状态规则重开/绑定 | 每个 bug 都重写 PRD；协调者直接修代码再自测放行 |
| 开发说通过，测试或真实旅程显示失败 | 先对齐基线、输入和入口，记录分歧，安排能区分原因的最小复现；保留独立 verdict | 以人数、角色资历或测试数量判定事实；让评审者统一口径后再评审 |
| 核心交付可本地完成，但可选发布/付费能力缺授权 | 将可选能力风险单独记录；继续已授权且不依赖它的工作，说明该能力未完成 | 擅自外部操作；把可选发布伪装为阻塞整个项目；把必需外部依赖误说成可选 |
| 用户以一个页面指出工具/角色能力不足 | 识别是在改页面、改产品目标还是改方法；意图不清时只问这个分界 | 自动再美化样例；从一次批评推出所有产品都要极简 |
| 输入仍在变化或两个任务将写同一产物 | 先稳定上游或串行交接；基线变化后重新派发有效工作项 | 为追求并发让下游基于未确认材料继续；合并失效输出 |
| 输入稳定、责任和输出互不覆盖，且当前阶段允许并行 | 在执行策略预算内并行；评审先各自提交，再综合分歧 | 无视阶段依赖或预算；共享他人结论污染独立评审 |

## 进度不是活动量

向用户报告时，指出哪项目标已有可观察证据、哪项仍是方向预览或计划、剩余不确定性由谁处理。文档增加、角色完成、测试数量增加都不单独意味着核心价值更接近交付。

某次尝试失败后，先判断是格式/工具使用问题、环境能力不足、实现缺陷，还是需要新的产品决定。可修正的内部机械问题在范围内修正后继续；每次进一步尝试都应带来新证据或改变一个有依据的条件。相同输入、相同失败、没有新信息时不要盲目重复派工；保留失败记录，选区分假设的检查，或说明具体外部阻塞。不得靠提高权限、降低标准、接受过期输出或越过预算维持表面推进。

## 跨角色交接的最小充分信息

在现有工作项和会议记录中传递：当前目标及受影响标准、已确认事实与未决假设、有效基线、问题为何属于该角色、预期证据、结束条件和禁止越界项。不复制整段历史，也不新建重复会议文档。

出现高于当前模式的风险时，提交证据给状态工具并等待规定的用户决策；本参考不能替代自动升级流程。停止时给出已尝试路径、不能继续的具体原因和用户最小决定，不把“继续”当成审批，也不将可自动核验的工作甩给用户。
