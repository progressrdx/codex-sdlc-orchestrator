# 评审判断：证据是否足以支持当前结论

用于当前关口的材料存在缺口、冲突或方案分歧时。结合已分配角色的专业视角，遵守主 Skill 的二元 verdict 和问题严重度规则；不增设关口，不代替其他角色或用户授权。

## 先确定要证明什么、现在该证明到哪一步

按「当前关口的主张 → 适用标准 → 证据及基线 → 反证/缺口 → 对目标的影响」评判。方案描述是设计证据，不是运行证据；没有运行结果不一定阻塞设计评审，却会阻塞要求运行结果的验收。不得为了显得严格向前索取尚不属于当前阶段的交付物。

| 材料中的情况 | 判断与处理 | 容易出现的错误 |
|---|---|---|
| PRD 有明确目标，却要求“智能、准确、体验好”而无判定口径 | 定位缺失的产品决定或可测试标准，说明其影响并要求责任人补齐 | 用更多形容词修饰；评审者自行发明阈值/业务政策 |
| readiness 已有可信设计、风险处理和可执行测试策略，但还没最终代码 | 按本关口核对可行性、关键不变量、验证接缝与未决风险；不能仅因未实现就拒绝 | 把 acceptance 的运行要求提前；反过来用设计批准代替最终验收 |
| 方案简单但满足已知负载、契约及运维约束，评审者偏好另一架构 | 检查实际风险与替代成本；偏好可作为非阻塞建议，不能无依据升为 major | “不够先进/不够优雅”即拒绝；把未来想象需求变成当前范围 |
| 通过报告绑定旧源码，当前源码发生相关变化 | 验收时拒绝陈旧证据，要求当前基线绑定及受影响验证；由状态规则决定哪些记录失效 | 按改动行数认为无需重测；在旧报告里直接换版本号 |
| 文档、mock 测试都通过，实际核心行为缺失 | 沿已确认目标找到缺失能力，按影响记录问题；拒绝把模型演示/脚手架当完整实现 | 以材料齐全、全绿或三方口头一致替代真实证据 |
| 两份结果矛盾 | 对齐输入、环境、启动路径、版本与观察方法，保留双方证据，要求最小可区分复现 | 投票、折中给过、只选最新或更乐观报告；未复现就宣布根因 |
| 只有非关键视觉偏好差异，其余要求与证据满足 | 明确这是建议而非违约；在无 blocker/major 且必需证据齐全时可 approve | 把审美偏好冒充可访问性缺陷；或把影响主任务的真实缺陷降为偏好 |

## 问题严重度依据后果，不依据措辞

- `blocker`：核心目标/强制条件无法满足，或存在不可继续的安全、数据、权限等风险；当前关口不能通过。
- `major`：有实质目标、正确性或验证缺口，需要处置；不能留着 major 同时 approve。
- `minor`：不妨碍当前关口目标成立的有限问题/建议；说明影响，不用它暗藏尚未解决的实质缺口。

必需证据缺失本身足以 reject，但要区分「尚未证明」和「已经证明产品错误」。不要编造缺陷根因以填表。问题严重度不替代状态工具对证据、风险或关口的硬约束；已有人类风险处置时核对身份、范围、有效性与工具允许条件，不自行豁免。

## 让拒绝有可执行的出口，让批准有清楚边界

对每个实质发现写明关联主张/标准、观察与引用、用户或系统后果、责任角色，以及什么最小新增证据或已授权修正能改变 verdict。不要要求重做无关阶段，也不要给出“全部完善”之类无法结束的动作。

仅给 `approve` 或 `reject`，不创造“有条件通过”。通过说明支持当前关口的证据与已记录残余限制，不代表永久正确；拒绝说明哪个必需主张不成立或尚未证明。独立结论提交前不阅读其他评审者结论；提交后分歧可以协商证据和行动，不能协商掉事实或权限边界。
